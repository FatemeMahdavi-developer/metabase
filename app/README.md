# فضای تحلیل — داشبوردساز Laravel 12 / Filament 3

رابط فارسی راست‌به‌چپ برای اتصال دیتابیس، ساخت گزارش و چیدن داشبورد. متابیس در اجرای برنامه استفاده نمی‌شود. ساختار گزارش مستقل، تنظیمات کارت، فیلتر و اتصال فیلتر به کارت بر اساس بررسی سورس محلی Metabase طراحی شده است.

## اجرای محلی

از فولدر `pending_updte` فایل `start.cmd` را اجرا کنید و به **http://127.0.0.1:8000/admin/analytics** بروید. اطلاعات ورود موجود در انتهای همین فایل است.

در PowerShell داخل `app`:

```powershell
& '..\.tools\php\php.exe' artisan migrate
& '..\.tools\php\php.exe' artisan db:seed --class=AnalyticsPostgresSeeder
$env:PATH = "$PWD\..\.tools\node;" + $env:PATH
npm.cmd run build
& '..\.tools\php\php.exe' artisan serve --host=127.0.0.1 --port=8000
```

دیتابیس پیش‌فرض انتشار PostgreSQL است. پیش از اجرای فرمان‌های راه‌اندازی، پروفایل `pgsql` را در `.env` شبکه تنظیم و migrationها را اجرا کنید. `AnalyticsPostgresSeeder` اتصال همان پروفایل Laravel را برای کاربر موجود پنل ثبت و جدول‌ها را همگام می‌کند؛ رمز داخل Seeder نوشته نمی‌شود. اگر چند کاربر دارید، `owner_email` را در گزینه‌های ابتدای Seeder مشخص کنید. `AnalyticsDemoSeeder` نیز برای سازگاری به همین Seeder ارجاع می‌دهد و دیگر فایل SQLite یا دادهٔ فروش ساختگی ایجاد نمی‌کند. گزارش و داشبورد را از جدول‌های واقعی پروژه می‌سازید؛ `AnalyticsClickHouseSeeder` برای داشبورد ClickHouse مستقل باقی است.

## اتصال دیتابیس

از «دیتابیس‌ها → اتصال دیتابیس» استفاده کنید. «آزمایش اتصال» ساختار را می‌خواند، «ذخیره و همگام‌سازی» اتصال را آزمایش و ذخیره می‌کند، و «ذخیره بدون اتصال» تنظیمات را برای سروری که هنوز در دسترس نیست نگه می‌دارد.

فرم ایجاد و تنظیم اتصال فقط PostgreSQL و ClickHouse دارد؛ پیش‌فرض PostgreSQL است. گزینه و مسیر فایل SQLite از فرم‌ها حذف شده‌اند و API هم ثبت یا آزمایش اتصال SQLite را رد می‌کند. اتصال‌های قدیمی SQLite از فهرست و انتخاب منبع پنهان‌اند؛ داده‌های آن‌ها حذف نمی‌شوند و برای استفادهٔ دوباره باید یک منبع PostgreSQL یا ClickHouse جایگزین تنظیم شود.

| درایور | ورودی‌ها | روش اجرا و مشاهدهٔ ساختار |
|---|---|---|
| PostgreSQL | host، port (5432)، database، username، password، SSL mode | PDO pgsql؛ schema/table/view و ستون‌ها و روابط؛ نشست فقط‌خواندنی و timeout |
| ClickHouse | host، HTTP port (8123)، database، username، password، HTTPS | HTTP با پارامترهای تایپ‌دار؛ `system.tables` و `system.columns`؛ محدودیت نتیجه و زمان |

سرورهای PostgreSQL و ClickHouse در محیط فعلی نصب نشده‌اند؛ طبق درخواست، اتصال واقعی و انتقال روی سرور داخل شبکه انجام می‌شود. افزونهٔ `pdo_pgsql` در PHP محلی فعال شده؛ ClickHouse به افزونهٔ اختصاصی احتیاج ندارد. برای اجرا در شبکه، `pdo_pgsql` و دسترسی HTTP لازم است. `pdo_sqlite` فقط برای خواندن دیتابیس قدیمی هنگام انتقال و fixtureهای تست استفاده می‌شود. رمزها با کلید Laravel رمزگذاری می‌شوند و API آن‌ها را برنمی‌گرداند؛ رمز خالی هنگام ویرایش، رمز قبلی را حفظ می‌کند. Join بر اساس پیشنهاد FK یا انتخاب دستی جدول و چند شرط ON است.

در فرم PostgreSQL، میزبان را به‌صورت نام میزبان یا IP و بدون `http://`، `https://` و پورت وارد کنید؛ پورت فیلد جداگانه دارد. خطای تنظیمات کنار همان فیلد فرم نمایش داده می‌شود. با خاموش‌بودن «آزمون اتصال پیش از ذخیره»، ثبت و ویرایش مشخصات بدون ارتباط با سرور انجام می‌شود؛ آزمون اتصال، همگام‌سازی جدول‌ها و اجرای گزارش به PostgreSQL قابل دسترس و اطلاعات اتصال معتبر نیاز دارند.

نام سرویس دارای زیرخط مانند `postgres_db` نیز در اعتبارسنجی میزبان PostgreSQL و ClickHouse پذیرفته می‌شود؛ میزبان باید از محیط PHP قابل شناسایی و دسترسی باشد. «نام» فقط عنوان اتصال در پنل است و «نام دیتابیس» پایگاهی است که جدول‌های پروژه در آن قرار دارند. برای نمونه، اگر در pgAdmin میزبان `db` و دیتابیس `soar_app` وارد می‌شود و Laravel در همان شبکه اجرا می‌شود، در ماژول نیز میزبان `db` و نام دیتابیس `soar_app` است. برای انتقال اصلاح زیرخط به شبکه، `AnalyticsController.php`، `Drivers/ClickHouseDriver.php` و `Filament/Resources/AnalyticsConnectionResource.php` را از مسیرهای متناظر داخل `app` منتقل کنید؛ این تغییر PHP به build جدید یا نصب بسته نیاز ندارد.

اصلاح میزبان دارای زیرخط با **۱۶ تست PHP / ۱۸۳ assertion** و یک تست واقعی Chrome تأیید شد: ثبت و ویرایش نام سرویس، حفظ رمز و نمایش خطای URL نامعتبر کنار فیلد. تست بومی پیش از اصلاح روی زیرخط شکست خورد و پس از اصلاح موفق شد. این بررسی، آزمون اتصال زندهٔ PostgreSQL نیست؛ درخواست ClickHouse نیز با HTTP جعلی بررسی شده است.

پس از اتصال، «مرور جدول‌ها» کلیدها، نوع ستون‌ها، اجازهٔ مقدار خالی، روابط و نمونهٔ ردیف‌ها را نمایش می‌دهد. نام و توضیح جدول/ستون، معنای ستون و پنهان‌بودن در انتخاب پیش‌فرض قابل ویرایش است؛ ساختار واقعی دیتابیس تغییر نمی‌کند و تنظیمات پس از همگام‌سازی حفظ می‌شوند. نمونهٔ فروش، نام‌های نمایشی فارسی دارد.

## یکتایی اتصال‌های پایگاه داده

نام نمایشی اتصال برای هر کاربر با حذف فاصلهٔ ابتدا/انتها و مقایسهٔ بدون حساسیت به حروف، یکتا است. هویت دیتابیس نیز ترکیب `driver + host + port + database` برای همان کاربر است؛ دو سرور متفاوت می‌توانند دیتابیس هم‌نام داشته باشند. تغییر نام نمایشی یا نام کاربری/رمز، مجوز ثبت دوبارهٔ همان مقصد را نمی‌دهد. نوع دیتابیس و پورت متفاوت، مقصد دیگری محسوب می‌شود؛ حروف نام دیتابیس تغییر داده نمی‌شوند. میزبان بدون حساسیت به حروف و با یکسان‌سازی نقطهٔ پایانی DNS مقایسه می‌شود.

اعتبارسنجی مشترک API، فرم Filament و مدل پیش از آزمون شبکه انجام می‌شود؛ خطا کنار `name` یا `configuration.database` نمایش داده می‌شود. دو fingerprint بدون رمز با قید یکتایی دیتابیس، ثبت هم‌زمان را نیز کنترل می‌کنند. این فیلدها در پاسخ API نمایش داده نمی‌شوند. تنظیمات اتصال همچنان رمزگذاری‌شده‌اند.

Migration تمام اتصال‌های تکراری قدیمی و شناسه‌های گزارش‌های وابسته را حفظ می‌کند. fingerprint تکراری‌های قبلی خالی می‌ماند؛ اعتبارسنجی برنامه‌ای این رکوردها را هم برای جلوگیری از ثبت تکراری جدید بررسی می‌کند. ویرایش بدون تغییر هویت، همگام‌سازی و تنظیم نام ستون‌های اتصال قدیمی ادامه دارد. برای پاک‌سازی دستی تکراری‌ها، اتصال‌های مورد استفادهٔ گزارش‌ها را ابتدا بررسی کنید. رفتار قید یکتایی و مقدار تهی با [مستندات PostgreSQL](https://www.postgresql.org/docs/current/ddl-constraints.html#DDL-CONSTRAINTS-UNIQUE-CONSTRAINTS) سازگار است.

اعتبارسنجی این اصلاح با اجرای کامل **۲۴۳ تست PHP / ۲۳۶۱ assertion** و یک سناریوی واقعی Chrome موفق بود؛ شامل خطای فیلد برای نام تکراری، مقصد تکراری با اطلاعات ورود متفاوت، اصلاح و ذخیرهٔ موفق فرم، قید دیتابیس و رقابت ثبت هم‌زمان، scope مالک و حفظ گزارش‌های رکوردهای قدیمی است. migration روی دیتابیس محلی پس از snapshot اجرا شد و build جدید آماده است. تست زندهٔ PostgreSQL همچنان به سرور داخل شبکه نیاز دارد.

برای انتقال این اصلاح به شبکه، `app/Domain/Analytics/ConnectionUniqueness.php`، نسخهٔ جدید Model اتصال، `AnalyticsController.php`، `AnalyticsConnectionResource.php`، `AnalyticsPostgresSeeder.php`، `resources/js/analytics/connections.js` و کل `public/build` را همراه migration جدید `database/migrations/2026_10_19_180000_add_analytics_connection_uniqueness.php` منتقل کنید. سپس از ریشهٔ Laravel اجرا کنید:

```bash
php artisan config:clear
php artisan migrate --force
php artisan view:clear
```

## ساخت گزارش و داشبورد

داشبوردساز اکنون داخل ناوبری اصلی همان پنل Filament قرار دارد. گروه «داشبوردساز» سه منوی «داشبوردها»، «گزارش‌ها» و «پایگاه‌های داده» دارد؛ منوی مستقل داخل صفحه حذف شده و منوهای دیگر پروژه، نوار بالا، حساب کاربری و انتخاب‌گر تم Filament در دسترس می‌مانند.

| صفحه | مسیر در پنل نمونه |
| --- | --- |
| فهرست داشبوردها | `/admin/analytics/dashboards` |
| نمایش و ویرایش داشبورد | `/admin/analytics/dashboards/{id}` |
| فهرست گزارش‌ها | `/admin/analytics/reports` |
| گزارش جدید / SQL جدید | `/admin/analytics/reports/new` و `?mode=native` |
| ویرایش گزارش ذخیره‌شده | `/admin/analytics/reports/{id}` |
| فهرست اتصال‌های دیتابیس | `/admin/analytics/databases` |
| مرور جدول‌ها و متادیتای اتصال | `/admin/analytics/databases/{id}` |

مسیر قدیمی `/admin/analytics` به فهرست داشبوردها هدایت می‌شود. لینک‌ها با کلاس‌های Resource/Page و `getUrl()` ساخته می‌شوند تا مسیر و پنل مقصد از تنظیمات Filament گرفته شود. گزارش ذخیره‌شده، داشبورد و مرور اتصال با آدرس مستقیم باز می‌شوند؛ refresh و دکمه‌های عقب/جلو مرورگر همان مقصد را باز می‌کنند. پس از ذخیرهٔ اولین گزارش، آدرس `new` با شناسهٔ گزارش جایگزین می‌شود.

سه فهرست، Resource واقعی Filament هستند: جدول Livewire با جست‌وجو، مرتب‌سازی، فیلتر مجموعه/نوع نمایش/موتور و Actionهای پنل. ایجاد داشبورد و مجموعه، مشخصات گزارش و ایجاد/ویرایش اتصال از فرم و مودال بومی استفاده می‌کنند. فرم اتصال بر اساس PostgreSQL و ClickHouse تغییر می‌کند؛ آزمون پیش از ذخیره اختیاری است و آزمون/همگام‌سازی جداگانه نیز در جدول وجود دارد. رمز فعلی به state فرم و API برگردانده نمی‌شود؛ خالی‌ماندن رمز آن را حفظ می‌کند. Query هر Resource به مالک جاری `Filament::auth()` محدود است؛ داشبوردهای مشترک مطابق نقش نمایش داده می‌شوند و حذف/کپی به مالک تعلق دارد. ویرایش مشخصات گزارش، تعریف Query و تنظیمات نمایش را حفظ و نسخهٔ قدیمی را رد می‌کند.

در فهرست گزارش‌ها، «کپی گزارش» فرم بومی نام، توضیح و مجموعه را باز می‌کند. کپی، شناسهٔ جدید و نسخهٔ۱ دارد و پرس‌وجو، نوع نمایش و تنظیمات نمودار را حفظ می‌کند؛ گزارش اصلی تغییر نمی‌کند. فیلتر «نوع نمایش» از `analytics.displays` ساخته می‌شود و کلیدهای واقعی Donut (`doughnut`) و Pivot (`pivot`) با عنوان فارسی قابل انتخاب‌اند.

فرم‌های داخل ویرایشگر نیز با Filament Forms و Livewire پیاده شده‌اند. تعریف فیلدها، اعتبارسنجی، گزینه‌های وابسته، تب‌های تنظیم نمودار، رنگ‌ها و Repeater شرط‌های Join در `app/Domain/Analytics/Filament/WorkbenchForms.php` قرار دارد و فرم در `AnalyticsWorkbench::workbenchForm()` رندر می‌شود. برچسب‌ها، راهنماها، عنوان‌ها و متن اکشن‌های فرم از `lang/fa/analytics.php` خوانده می‌شوند. گزینه‌های دامنه‌ای دارای مقدار ذخیره‌شونده، مانند درایور، SSL، نوع نمودار، Join، محاسبه، بازهٔ زمانی، عملگر فیلتر و نقش دسترسی، در `app/Enums` تعریف شده‌اند و متد `label()` آن‌ها ترجمه را از `lang/fa/enums.php` می‌خواند؛ بنابراین مقدارهای ذخیره‌شدهٔ قبلی تغییر نمی‌کنند. ذخیرهٔ گزارش، تنظیم داشبورد/تب/کارت، انتخاب منبع و ستون، فیلتر و مقدار پیش‌فرض، محاسبه، گروه‌بندی، Sort/Limit، ستون سفارشی، SQL و پارامترها، اشتراک و رفتار کلیک از این مسیر استفاده می‌کنند. نام جدول و ستون همچنان از انتخاب زبان سراسری پیروی می‌کند.

JavaScript پیش‌نویس Notebook، نمودار، GridStack و ارتباط نتیجهٔ فرم با آن‌ها را مدیریت می‌کند؛ فیلدهای فرم از HTML تولیدشده با JavaScript ساخته نمی‌شوند. مسیر `resources/js/analytics/native-forms.js` داده و گزینه‌های پیش‌نویس را به فرم PHP می‌دهد و نتیجهٔ معتبر را به ویرایشگر برمی‌گرداند. بررسی مجوزها، منابع، نوع ستون‌ها و نسخهٔ رکورد هنگام ذخیره در سرور دوباره انجام می‌شود. خطای ذخیره، فرم را باز نگه می‌دارد. هنگام تغییر ورودی وابسته، فرم تا پایان پاسخ Livewire غیرفعال است. کامپوننت‌های Filament از فایل‌های محلی بارگیری می‌شوند؛ `resources/js/filament-forms.js` کارخانهٔ اصلی Textarea خود Filament را برای اکشن‌های پویا ثبت می‌کند.

اطلاعات داخلی ماژول (مجموعه، گزارش، داشبورد، تب، کارت، فیلتر، اتصال فیلتر، عضو و نسخهٔ داشبورد) با مدل‌های Eloquent خوانده و نوشته می‌شوند. تراکنش و کنترل نسخه حفظ شده‌اند. SQL کامپایل‌شده برای منبع خارجی PostgreSQL/ClickHouse و امکان نوشتن SELECT توسط کاربر باقی است؛ این جدول‌های پویا الزاماً مدل Laravel ندارند و تبدیل آن‌ها به مدل‌های ثابت Eloquent، قابلیت گزارش‌گیری را محدود می‌کند.

برای انتقال این تغییر به شبکه، فایل‌های PHP، مدل‌های جدید، Blade، JavaScript و `vite.config.js` را همراه کل خروجی `public/build` منتقل کنید. Build را روی سیستم دارای Node و وابستگی‌های نصب‌شده با `npm run build` انجام دهید. در شبکه `php artisan optimize:clear` را اجرا کنید؛ این بازطراحی به migration جدید یا پکیج Composer/NPM جدید نیاز ندارد. Build از فایل کامپوننت نسخهٔ نصب‌شدهٔ Filament در `vendor` استفاده می‌کند.

آزمون‌های این بازطراحی: `NativeAnalyticsWorkbenchFormsTest` همهٔ فرم‌های ثبت‌شده، اعتبارسنجی، تعویض فرم و مجوز جست‌وجوی مقادیر را بررسی می‌کند؛ `NativeFormState.test.mjs` حفظ چند مقدار، صفر، false، تهی، بازه و تاریخ نسبی را پوشش می‌دهد. در Chrome، فایل `native-workbench-forms.spec.js` ذخیره و بازخوانی واقعی گزارش/داشبورد، تب، متن، Join، فیلتر، محاسبه، ستون سفارشی، تنظیم نمودار، اتصال فیلتر و رفتار کلیک را بررسی می‌کند. `postgres-table-names.spec.js` انتخاب منبع دو زبانه و ویرایش SQL را پوشش می‌دهد. سرور خارجی در محیط توسعه در دسترس نیست؛ کاتالوگ PostgreSQL آزمون و ذخیره‌سازی داخلی واقعی‌اند، اما پاسخ اجرای کوئری خارجی در مرورگر شبیه‌سازی می‌شود. فرم‌های PostgreSQL و جلوگیری از اتصال تکراری نیز در آزمون‌های مرورگر موجود اجرا شده‌اند.

پنجرهٔ بومی پس از بسته‌شدن در DOM باقی می‌ماند؛ هر بار بازشدن، شناسهٔ دورهٔ تازه دارد. پاسخ دیررس جزئیات رکورد یا مقاصد رفتار کلیک فقط برای پنجرهٔ باز و همان دوره اعمال می‌شود؛ پس از بستن و بازکردن پنجره‌ای دیگر، محتوا یا انتخاب جدید را تغییر نمی‌دهد. شنونده‌های پنجرهٔ قبلی نیز هنگام بسته‌شدن آزاد می‌شوند.

1. «گزارش جدید» یا «ساخت گزارش از این جدول»: دیتابیس و جدول را انتخاب کنید.
2. ویرایشگر مرحله‌ای، داده‌ها را آبی، فیلتر را بنفش و محاسبه/گروه‌بندی را سبز نمایش می‌دهد. انتخاب‌گرهای محاسبه، فیلتر، تاریخ و ستون جدا هستند. حداکثر ۱۰ محاسبه، ۶ بُعد، ۵ Join با نوع LEFT/INNER/RIGHT/FULL و تا ۵ شرط ON در هر اتصال پشتیبانی می‌شود. ستون‌ها و شرط‌ها از کاتالوگ معتبر انتخاب می‌شوند؛ Join به FK محدود نیست. تاریخ به روز، هفته، ماه، فصل و سال گروه‌بندی می‌شود. افزودن اولین گروه به گزارش تک‌عددی، نمایش را به جدول تغییر می‌دهد تا همهٔ گروه‌ها دیده شوند؛ Sort قبلی که دیگر ستون خروجی نیست حذف می‌شود.
3. Notebook بخش‌های مستقل «داده، اتصال داده‌ها، ستون محاسباتی، فیلتر، خلاصه‌سازی، مرتب‌سازی، محدودیت ردیف‌ها» را به همین ترتیب نمایش می‌دهد. دکمه‌های مستقیم کنار منبع و پس از خلاصه‌سازی برای افزودن بخش وجود دارند؛ منوی «+» نیز بر اساس مرحلهٔ فعلی عمل می‌کند. ستون محاسباتی پیش از فیلتر قرار می‌گیرد. Sort انتخاب‌گر جست‌وجوی ستون، جهت قابل تغییر روی کارت، چند ستون بدون تکرار، جابه‌جایی و حذف دارد. Limit ورودی مستقل دارد و هنگام خروج از ورودی یا Enter اعمال می‌شود؛ مقدار خالی آن را حذف می‌کند. عدد صحیح مثبت، از جمله ۵۰۰۰، مجاز است. روی هر بخش، پیش‌نمایش فقط عملیات تا همان بخش را با حداکثر ۱۰ ردیف اجرا می‌کند؛ Limit کوچک‌تر را حفظ می‌کند و تعریف پرسش را تغییر نمی‌دهد. کارت‌های محاسبه، فیلتر، گروه‌بندی، ستون سفارشی و Sort قابل جابه‌جایی‌اند؛ ترتیب نامعتبر ستون‌های وابسته رد می‌شود.
   پس از خلاصه‌سازی، افزودن ستون سفارشی یا فیلتر روی خروجی، مرحلهٔ بعد را ایجاد می‌کند. تا ۵ مرحلهٔ بعدی می‌توانند خروجی قبلی را فیلتر، به جدول دیگری Join یا دوباره خلاصه کنند. هر مرحله انتخاب‌گر Join با چهار نوع و چند شرط ON، ستون محاسباتی و انتخاب ستون خروجی دارد؛ فرمول می‌تواند از محاسبهٔ قبلی یا ستون جدول متصل‌شده استفاده کند. حذف ستون یا Join، شرط‌ها و Sort وابسته را پاک می‌کند و سایر تنظیمات معتبر را حفظ می‌کند.
   فرم بومی ستون سفارشی شامل نام ستون، فرمول، تکمیل خودکار با صفحه‌کلید، انتخاب‌گر قابل جست‌وجوی ستون/تابع، راهنمای امضا و مثال، ترکیب ستون‌های متنی و خطای زنده است. `[مبلغ کل] * 0.09` و کلید پایدار `[total]` هر دو پذیرفته می‌شوند؛ نام نمایشی به کلید پایدار تبدیل می‌شود تا تغییر برچسب، فرمول ذخیره‌شده را خراب نکند. اعتبارسنجی فرمول، SQL داده‌ها را اجرا نمی‌کند. توابع پشتیبانی‌شده: `abs`، `round`، `ceil`، `floor`، `upper`، `lower`، `length`، `concat`، `trim`، `ltrim`، `rtrim`، `substring`، `replace`، `if`، `case` چندشرطی، `contains`، `startsWith`، `endsWith`، `between`، `not`، `coalesce`، `isNull` و `notNull`؛ عملگرهای عددی، مقایسه و `and/or` نیز موجودند.
   Limit پرسش از سقف پیش‌نمایش جداست: تنظیمات پیش‌فرض `analytics.preview_row_limit=2000` برای ردیف‌های خام و `analytics.preview_aggregate_limit=10000` برای خروجی خلاصه‌سازی است. سقف نمایشی محاسبات مراحل قبلی را قطع نمی‌کند؛ Limit صریح همان مرحله در SQL اعمال می‌شود. رسیدن دقیق به Limit انتخاب‌شده، اشتباهاً «نتیجه بریده‌شده» گزارش نمی‌شود. گزارش‌های قدیمی با Limit فاقد `limit_explicit`، سقف نمایشی قبلی خود را حفظ می‌کنند.
4. نمایش عدد، جدول، ستونی، خطی، ناحیه‌ای، دایره‌ای، حلقه‌ای، پراکندگی، Pivot، قیف، پیشرفت یا گیج را انتخاب کنید. پنل تنظیمات تب‌های داده‌ها، نمایش، محورها و قالب‌بندی دارد: انتخاب ستون، صفحه‌بندی، تجمعی/افقی، خطوط/نقاط، محدودهٔ محور، رنگ، راهنما، هدف، پیشوند/پسوند و اعشار. Pivot دو بُعد و مجموع‌های ردیف/ستون دارد. جدول با کلیک عنوان ستون مرتب و صفحه‌بندی می‌شود.
5. «داشبورد جدید → افزودن گزارش»: گزارش ذخیره‌شده را انتخاب کنید؛ کارت‌ها را بکشید و اندازه‌شان را تغییر دهید. چیدمان دسکتاپ ۲۴ ستون و موبایل یک ستون است. برای حفظ چیدمان اصلی، ذخیره در نمایش دسکتاپ انجام می‌شود.
6. متن Markdown و لینک، تب‌های قابل نام‌گذاری و کپی، عنوان و نمایش اختصاصی هر کارت را تنظیم کنید. تنظیم نمایش کارت، گزارش پایه را تغییر نمی‌دهد.
7. فیلتر متن/عدد/تاریخ/بله‌وخیر/گروه‌بندی زمانی ایجاد و برای **هر کارت** ستون سازگار را انتخاب کنید. ستون‌های مراحل بعدی با عنوان مرحله نمایش داده می‌شوند؛ فیلتر روی همان مرحله اعمال می‌شود، از جمله ستون جدول Joinشده، محاسبهٔ خروجی قبلی یا ستون محاسباتی. گروه‌بندی زمانی نیز می‌تواند به بُعد تاریخی مرحلهٔ بعد متصل شود. فیلتر بی‌اتصال روی آن کارت اثری ندارد. پیش‌فرض، الزام انتخاب، فهرست مقادیر، وابستگی به والد و اعمال خودکار/دستی پشتیبانی می‌شود. پیشنهاد مقادیر از منبع و با لحاظ فیلترهای دیگر خوانده می‌شود؛ جست‌وجو سمت دیتابیس و صفحه‌بندی ۱۰۰تایی دارد. فیلتر تاریخ شامل تمام روز است، حتی برای timestamp.
8. در تنظیمات کارت، «رفتار کلیک» را برای کل کارت یا هر ستون جدا انتخاب کنید: منوی بررسی، تغییر چند فیلتر، رفتن به داشبورد/پرسش با اتصال مقادیر، لینک یا بدون عملیات. لینک از `{{column:status}}`، `{{parameter:period}}` و `{{value}}` پشتیبانی می‌کند؛ مقدار در URL کدگذاری می‌شود و متن لینک قابل تنظیم است. کلیک عنوان ستون، عملیات ستون را نشان می‌دهد. CSV از نتیجهٔ فعلی قابل دریافت است.
9. «ذخیره» تمام پیش‌نویس را در یک تراکنش ثبت می‌کند؛ «انصراف» به نسخهٔ ذخیره‌شده برمی‌گردد. تاریخچه و بازیابی نسخه، کپی داشبورد با گزارش مشترک یا کپی گزارش‌ها، اشتراک با کاربران موجود به‌صورت viewer/editor و تازه‌سازی خودکار موجود است. نسخه‌گذاری، ذخیرهٔ هم‌زمان روی نسخهٔ قدیمی را با خطای 409 متوقف می‌کند.

SQL بومی یک SELECT/CTE خواندنی است. SQL به‌صورت پیش‌نمایش رنگ‌بندی‌شده نشان داده می‌شود؛ دکمهٔ «ویرایش SQL» فرم Textarea بومی Filament را باز می‌کند. مرور و درج ستون‌ها و فرم پارامترها در دسترس‌اند. متغیرها را **بدون نقل‌قول** مثل `WHERE city = {{city}}` بنویسید؛ پنل متغیرها نام‌ها را تشخیص می‌دهد و نوع، پیش‌فرض و الزامی‌بودن را تنظیم می‌کند. `[[ AND city = {{city}} ]]` در صورت خالی‌بودن متغیر اختیاری حذف می‌شود؛ مقادیر bind می‌شوند. اتصال فیلتر داشبورد به متغیر SQL، عملگر «برابر با» و یک مقدار می‌پذیرد. دستورات نوشتن و چند دستور رد می‌شوند.

افزودن پرسش به داشبورد در پنل کناری انجام می‌شود. انتخاب نوع فیلتر، تنظیمات و انتخاب ستون مقصد روی هر کارت سه بخش مجزا هستند. فیلترهای مشاهده از پنجرهٔ تاریخ (شامل دوره‌های آماده)، بازهٔ عددی یا انتخاب/جست‌وجوی مقادیر استفاده می‌کنند. هنگام ذخیرهٔ پرسش می‌توان «پس از ذخیره به داشبورد اضافه شود» را انتخاب کرد. فرم رفتار کلیک فقط ورودی‌های مربوط به رفتار انتخاب‌شده را نمایش می‌دهد. در فرم‌های طولانی، بدنه اسکرول می‌شود و عنوان و دکمه‌های اعمال و انصراف در دسترس می‌مانند.

### فیلتر، جست‌وجو و بررسی جزئیات

- فیلتر متن، عدد، تاریخ، بله/خیر و گروه‌بندی زمانی؛ شرط برابر/نابرابر، چند مقدار، بازه/خارج از بازه، مقایسهٔ عدد/تاریخ، شامل/شامل نیست/شروع/پایان متن، NULL و متن تهی. شرط متن جزئی، گزینهٔ حساسیت به حروف دارد. صفر و «خیر» با پاک‌کردن فیلتر تفاوت دارند.
- انتخاب‌گر مقادیر با جست‌وجوی سمت دیتابیس، صفحهٔ بعد، انتخاب مقادیر صفحه، حفظ انتخاب هنگام جست‌وجو، حذف تکی و ورود مقدار دلخواه؛ جست‌وجو به اولین ۱۰۰ گزینه محدود نیست. هر صفحه و هر انتخاب چندتایی حداکثر ۱۰۰ مقدار دارد. NULL انتخاب مستقل است و با انتخاب‌های معمولی ترکیب نمی‌شود.
- فهرست، جست‌وجو و ورودی آزاد برای متن/عدد؛ پیش‌فرض عادی، NULL و تاریخ نسبی؛ دوره‌های روز/هفته/ماه/فصل/سالِ گذشته، جاری و آینده، شامل دورهٔ جاری یا حذف بازه. تاریخ نسبی به صورت تعریف ذخیره و هنگام اجرا دوباره محاسبه می‌شود. فیلتر وابسته از دیتابیس مقدار می‌گیرد، بدون والد غیرفعال است و با تغییر والد بازنشانی می‌شود. اعمال خودکار و دستی رعایت می‌شوند؛ کلیک چند فیلتر را یکجا تغییر می‌دهد.
- تاریخ نسبی علاوه بر داشبورد، در فیلتر ذخیره‌شدهٔ Notebook و فرم فیلتر منوی ستون نتیجه قابل انتخاب است. بازکردن دوبارهٔ پرسش، تعریف دوره را حفظ می‌کند و با گذشت زمان بازه هنگام اجرا تغییر می‌کند. انتخاب اجزای تاریخ، روز هفته با مبنای دوشنبه، ماه، فصل یا ساعت را شامل یا حذف می‌کند؛ تاریخ مشخص، بازه و شرط خالی/دارای مقدار نیز پشتیبانی می‌شوند. SQL بومی از فیلتر تاریخ مشخص روی خروجی پشتیبانی می‌کند؛ فرم دورهٔ نسبی فقط برای پرسش ساختاریافته فعال است.
- سلول جدول، نقاط نمودار، عدد، قیف، پیشرفت، گیج و سلول‌ها/مجموع‌های Pivot، مختصات ستون و ردیف اصلی را ارسال می‌کنند. منوی بررسی بر اساس نوع و نقش داده ساخته می‌شود: مقایسه/فیلتر، Sort ستون، توزیع و خلاصه‌سازی، رکوردهای زیرین، تفکیک و بزرگ‌نمایی تاریخ.
- فیلتر مقدار روی نتیجهٔ خلاصه‌شده به مرحلهٔ بعد اضافه می‌شود. برای رکوردهای زیرین، مانند سورس Metabase، مراحل انتهایی فاقد خلاصه‌سازی کنار گذاشته می‌شوند؛ در آخرین مرحلهٔ خلاصه‌سازی، محاسبه، گروه‌بندی، Sort، Limit و انتخاب ستون حذف و گروه‌های کلیک‌شده با مسیر قابل ردیابی فیلتر می‌شوند. مراحل پیشین و Join و فیلترهای مراحل باقی‌مانده حفظ می‌شوند. بزرگ‌نمایی تاریخ فقط بازهٔ کلیک‌شده و دورهٔ ریزتر را اعمال می‌کند و سایر دسته‌های نمودار را حفظ می‌کند.
- شناسهٔ رکورد و کلید خارجی، پنل جزئیات و رکوردهای مرتبط دارند. مسیر بررسی با بازگشت و تاریخچه نمایش داده می‌شود؛ پرسش و داشبورد اصلی تغییر نمی‌کنند. مسیر حداکثر هشت عمل دارد. مالک منبع می‌تواند نتیجهٔ بررسی را به عنوان پرسش جدید ذخیره کند. SQL بومی هم فیلتر و مرتب‌سازی خروجی با مقادیر bind شده دارد؛ روابط PK/FK در SQL دلخواه حدس زده نمی‌شوند.
- جدول نتیجه، جست‌وجوی محلی در ردیف‌های نمایش‌داده‌شده دارد و نام آن این محدودیت را مشخص می‌کند. برای جست‌وجو در کل دیتابیس از فیلتر پرسش استفاده کنید. جست‌وجوی کتابخانه نام، توضیح، مجموعه و نوع نمایش را بررسی و شکل فارسی/عربی «ی/ک» را یکسان می‌کند.

در API کلیک، مقدار/نوع ستون از کلاینت پذیرفته نمی‌شود؛ سرور آن را از نتیجهٔ مجاز و امضای نتیجه استخراج می‌کند. بررسی داشبورد مشترک از کارت ذخیره‌شده و مسیر عملیات مجاز بازسازی می‌شود. رفتن به پرسش مقصد نیز اتصال مقادیر را روی سرور بررسی می‌کند و پرسش مقصد را تغییر نمی‌دهد.

### ظاهر ویجت‌ها و حفظ رنگ در بررسی داده

فایل ارسالی `theme-cleaned.css` مبنای فعلی تم پنل Filament و فضای تحلیل است؛ ظاهر و پالت سری‌های نمودار نیز از تصاویر روشن و تیرهٔ ارسال‌شده پیروی می‌کنند. گوشهٔ ۱۶ پیکسلی، کادر و عنوان کارت‌ها با قواعد صریح `.soar-dashboard-widget .fi-section` و عنوان ۱۶ پیکسلی/وزن۹۰۰ در همان CSS هماهنگ‌اند. کارت‌های سفید/مشکی، ستون‌های گرد، خطوط ظریف و راهنمای نقطه‌ای با دادهٔ واقعی گزارش تولید می‌شوند؛ عددها و درصدهای تصویر نمونه ثابت یا جایگزین داده نشده‌اند.

قواعد فایل ارسالی در `resources/css/panel-theme.css` حفظ شده‌اند؛ فقط `@import` تم vendor و `@config` مخصوص ابزار ساخت قبلی حذف شده‌اند. تم پایهٔ Filament جداگانه بارگذاری می‌شود و CSS کاربر پس از آن، با hookِ `STYLES_AFTER`، فقط یک بار اضافه می‌شود. قواعد سازگاری انتهای فایل، منوی کاربر و دکمهٔ اصلی نوار کناری Filament را در پنلی که کنترل‌های سفارشی SOAR ندارد حفظ می‌کنند. فضای تحلیل نیز از همان سایدبار اصلی، حالت جمع‌شدهٔ دسکتاپ و کشوی موبایل استفاده می‌کند. رنگ فرم‌ها، پنجره‌ها، ورودی‌ها و Tooltip در `analytics-theme.css` به متغیرهای همین تم متصل است؛ `analytics-filament.css` سازگاری ویرایشگرها را با صفحه و مودال بومی فراهم می‌کند. همهٔ CSSهای فضای تحلیل از یک ورودی JavaScript و با ترتیب پایه، تم، سازگاری Filament و نام‌های متادیتا ساخته می‌شوند؛ در نتیجه مرورگر فقط یک فایل `analytics-*.css` دریافت می‌کند و قوانین تم دوباره بارگذاری نمی‌شوند. فونت وزیر داخل پروژه قرار دارد و بستهٔ npm/composer جدیدی نصب نشده است.

## زبان نام جدول‌ها و ستون‌ها

پیش‌فرض «نام اصلی دیتابیس» است: نام ستون با همان حروف و زیرخط‌های ذخیره‌شده در دیتابیس نمایش داده می‌شود. جدول PostgreSQL با نام دیتابیس اتصال نمایش داده می‌شود؛ مثلاً `public.users` در دیتابیس `unisq` به شکل `unisq.users` دیده می‌شود. برای schema دیگر، `audit.users` به شکل `unisq.audit.users` نمایش داده می‌شود تا جدول‌های هم‌نام متمایز بمانند. نام دیتابیس از تنظیمات همان اتصال خوانده می‌شود و برای همهٔ اتصال‌ها ثابت نیست. نام اصلی و کلید جدول در SQL، Join و تعریف گزارش همچنان `schema.table` است؛ نام دیتابیس صرفاً به عنوان نمایشی اضافه می‌شود. کاتالوگ‌های ذخیره‌شدهٔ قبلی نیز بدون Sync دوباره با همین قاعده نمایش داده می‌شوند.

انتخاب‌گر «زبان نام جدول‌ها و ستون‌ها» سه حالت «نام اصلی دیتابیس»، «فارسی» و `English` دارد؛ ترجیح در مرورگر و به تفکیک کاربر ذخیره می‌شود. در دو زبان نیز نام دیتابیس قبل از عنوان ترجمه‌شدهٔ جدول می‌آید؛ نام و alias ستون‌ها تغییر نمی‌کند. انتخاب‌گر در نوار فضای تحلیل و هنگام انتخاب منبع در دسترس است؛ در پنجرهٔ انتخاب منبع تنها کنترل داخل همان پنجره دیده می‌شود.

بازبینی نمایش `unisq` با **۶۷ تست PHP / ۷۴۱ assertion**، هر **۶ تست Node نام‌گذاری** و **سه سناریوی Chrome در اجراهای نهایی‌شان** موفق بود. مرورگر پیش‌فرض فرم و تعویض موتور، نمایش جدول در سه زبان، تفکیک schemaها و تولید `SELECT * FROM "public"."orders"` را تأیید کرد. کاتالوگ قبلی و sync، حفظ کلیدهای Join و جایگزینی پیشوند پس از تغییر دیتابیس در تست PHP بررسی شدند. این تست‌ها به سرور PostgreSQL داخل شبکه متصل نمی‌شوند؛ build جدید نیز آماده است.

در «دیتابیس‌ها ← نام دیتابیس ← تنظیمات جدول/ستون»، نام اصلی فقط خواندنی و دو ورودی مستقل برای نام نمایشی فارسی و انگلیسی وجود دارد. خالی‌کردن هر ورودی فقط ترجمهٔ همان زبان را پاک می‌کند؛ نبود ترجمه باعث نمایش نام اصلی می‌شود. نام‌های نمایشی قبلی نیز قابل استفاده می‌مانند و Sync، نام‌های تنظیم‌شده را حفظ می‌کند. جست‌وجوی منبع و جدول با هر سه نام کار می‌کند.

این انتخاب در کاتالوگ، Notebook، Join، انتخاب ستون، نتیجه و Drill down اعمال می‌شود. نام‌گذاری فقط نمایشی است: کلید ستون، SQL، تعریف پرسش، مقدار داده‌ها و نام‌های سفارشی ستون محاسباتی/خلاصه‌سازی/aliasِ SQL تغییر نمی‌کنند. فرمول می‌تواند نام نمایشی فارسی یا انگلیسی ستون را بپذیرد؛ بک‌اند آن را به کلید اصلی تبدیل می‌کند و نام مبهم را رد می‌کند. این قابلیت زبان کل رابط یا محتوای داده‌ها را تغییر نمی‌دهد.

برای انتقال آفلاین بازطراحی، فایل‌های `Analytics*` و زیردایرکتوری‌های مربوط در `app/Filament/Resources` و `app/Filament/Pages`، پوشهٔ `app/Domain/Analytics/Filament`، viewهای `resources/views/filament`، JavaScript و CSS تغییرکرده و `vite.config.js` را همراه **کل `public/build` و `manifest.json` و پوشهٔ کامل `public/fonts/vazir`** منتقل کنید. کلاس‌ها و منوهای موجود پروژهٔ مقصد را حفظ کنید؛ Provider پنل فعلی باید Resource/Pageهای جدید را با `discoverResources`/`discoverPages` کشف یا صریحاً ثبت کند. جدول‌های `analytics_*` موجود و داده‌های ذخیره‌شده نیاز به ساخت مجدد یا اجرای Seeder ندارند.

اصلاحات بارگذاری در شبکه، علاوه بر فایل‌های بالا، به انتقال این فایل‌ها نیاز دارند:

- `app/Support/AnalyticsAssets.php`
- `resources/views/filament/pages/analytics-studio.blade.php` و `resources/views/filament/partials/panel-theme.blade.php`
- `resources/views/vendor/filament-panels/components/sidebar/index.blade.php`
- `resources/js/analytics/theme.js` و **کل خروجی بازسازی‌شدهٔ `public/build`** همراه manifest و همهٔ فایل‌های assets

قالب سایدبار، منوها و hookهای بومی Filament را حفظ می‌کند و اسکریپت `data-analytics-sidebar-state` آن مقدار خراب یا قدیمی `localStorage.collapsedGroups` را مدیریت می‌کند؛ گروهی که دیگر قابلیت جمع‌شدن ندارد مخفی نمی‌شود و حالت Alpine هنگام ناوبری SPA نیز هماهنگ می‌ماند. اگر قالب سایدبار پروژهٔ مقصد از قبل سفارشی شده است، همین بلوک اسکریپت را با قالب موجود ادغام کنید؛ جایگزینی کامل قالب سفارشی ممکن است تغییرات و منوهای اختصاصی مقصد را از بین ببرد.

با انتقال build آماده و فونت‌های محلی، برای این تغییر به نصب بستهٔ جدید یا اجرای npm داخل شبکه نیاز نیست. در Provider پنل مقصد، hookِ بارگذاری تم و `->font('Vazir', url: asset('fonts/vazir/font-face.css'), provider: LocalFontProvider::class)` را مانند `AdminPanelProvider` ثبت کنید؛ نسخهٔ تم قدیمی را هم‌زمان دوباره بارگذاری نکنید. پس از انتقال فایل‌ها، سرور `npm run dev` را متوقف کنید و از **ریشهٔ پروژهٔ Laravel** در PowerShell اجرا کنید:

```powershell
Remove-Item -LiteralPath public/hot -ErrorAction SilentlyContinue
php artisan view:clear
php artisan route:clear
php artisan filament:clear-cached-components
php artisan livewire:publish --assets
```

فرمان `filament:clear-cached-components` در Filament نصب‌شدهٔ همین پروژه موجود است و cache کشف کامپوننت‌ها را پاک می‌کند. مسیرهای تازه با `php artisan route:list --path=analytics` قابل بررسی‌اند؛ اگر پروژهٔ مقصد برای انتشار route cache می‌سازد، آن را پس از انتقال نسخهٔ جدید بازسازی کنید.

اگر Console خطای CORS برای `http://[::1]:5173/@vite/client` یا `resources/js/analytics.js` نشان می‌دهد، صفحه به سرور توسعهٔ Vite اشاره می‌کند. رفتار معمول `@vite` با وجود `public/hot`، حتی در production و با build آماده، استفاده از نشانی داخل آن فایل است. بارگذاری تم پنل و ویرایشگر تحلیل اکنون از `AnalyticsAssets` عبور می‌کند: روی میزبان شبکه یا هر محیط غیر از `local`، فایل‌های manifest را می‌خواند و `public/hot` قدیمی را برای همین بارگذاری نادیده می‌گیرد. HMR فقط در محیط `local` و روی `localhost`، `127.0.0.1` یا `::1` فعال می‌ماند. تنظیمات Vite اصلی برنامه، nonce مربوط به CSP و ویژگی‌های سفارشی تگ‌ها حفظ می‌شوند؛ برای سایر مصرف‌کنندگان Vite نیز فایل `public/hot` را طبق دستورات بالا از استقرار حذف کنید.

فرمان انتشار Livewire هشدار `The published Livewire assets are out of date` را برای فایل‌های منتشرشده با نسخهٔ نصب‌شده هماهنگ می‌کند و به اینترنت نیاز ندارد. اگر وابستگی‌های Node موجودند، `npm run build` را پیش از این دستورات اجرا کنید؛ در غیر این صورت کل `public/build` شامل manifest و فایل‌های assets را از build همان پروژه بیرون شبکه منتقل کنید. سپس `Ctrl+F5` بزنید: در Network باید فایل `build/assets/analytics-*.js` از سرور خود پنل با وضعیت ۲۰۰ دریافت شود و درخواستی به پورت `5173` وجود نداشته باشد. فایل `public/hot` را همراه استقرار منتقل نکنید؛ اجرای دوبارهٔ `npm run dev` آن را بازسازی می‌کند.

در شبکهٔ داخلی با HTTP، ممکن است `crypto.randomUUID` وجود نداشته باشد؛ این API طبق [مستندات مرورگر](https://developer.mozilla.org/en-US/docs/Web/API/Crypto/randomUUID) به محیط امن نیاز دارد. تولید شناسهٔ عناصر رابط در `resources/js/analytics/uid.js` ابتدا API اصلی و سپس `getRandomValues` را به کار می‌برد؛ API دوم [روی HTTP نیز قابل استفاده است](https://developer.mozilla.org/en-US/docs/Web/API/Crypto/getRandomValues). برای مرورگر فاقد هر دو API، مسیر جایگزین فقط شناسهٔ محلی رابط تولید می‌کند و کاربرد امنیتی ندارد. بستهٔ جدید، تغییر تنظیمات مرورگر یا تغییر سراسری `crypto` لازم نیست؛ فایل‌های خروجی جدید باید همراه manifest به مقصد منتقل شوند.

## انتشار با PostgreSQL و انتقال دیتابیس قبلی

پیش‌فرض `config/database.php` و تنظیمات نمونه، PostgreSQL است؛ انتخاب منبع در پنل و API فقط `pgsql` و `clickhouse` را می‌پذیرد. اتصال داخلی SQLite برای fixtureهای تست و خواندن دیتابیس قدیمی هنگام انتقال باقی مانده است. چون PostgreSQL فقط داخل شبکه در دسترس است، `.env` محلی این محیط برای کارکرد پنل و تست‌ها تغییر نکرده و انتقال واقعی اجرا نشده است.

در `.env` **سرور داخل شبکه**، مشخصات واقعی PostgreSQL را تنظیم کنید. در تنظیمات نمونه، `db` میزبان و `unisq` نام دیتابیس است؛ نام کاربری و رمز را با مقادیر همان سرور جایگزین کنید. پیش‌فرض فرم اتصال PostgreSQL و عنوان اتصال جدید Seeder نیز `unisq` است؛ اتصال‌های ذخیره‌شده و دیتابیس واقعی با این تغییر نام‌گذاری نمی‌شوند. اگر `DB_URL` تنظیم شده است، آن نیز باید به مقصد PostgreSQL اشاره کند؛ Laravel آن را بر فیلدهای جداگانه مقدم می‌داند.

```dotenv
DB_CONNECTION=pgsql
DB_HOST=db
DB_PORT=5432
DB_DATABASE=unisq
DB_USERNAME=your_database_user
DB_PASSWORD=your_database_password
DB_SSLMODE=prefer
LEGACY_SQLITE_DATABASE=C:/path/to/previous/database.sqlite
```

اگر دیتابیس فعلی PostgreSQL پروژه از قبل داده دارد، **انتقال کامل SQLite را اجرا نکنید**؛ فقط migrationهای لازم ماژول را با روال انتشار پروژه اجرا و اتصال گزارش را ثبت کنید. فرمان انتقال عمداً مقصد دارای داده را رد می‌کند و برای ادغام دو دیتابیس طراحی نشده است.

برای انتقال دیتابیس قبلی همین برنامه به یک مقصد PostgreSQL تازه و خالی، ابتدا از فایل SQLite و `.env` نسخهٔ پشتیبان بگیرید، نوشتن درخواست‌ها و workerهای صف را متوقف کنید و **همان `APP_KEY` قبلی را نگه دارید** تا رمز اتصال‌های ذخیره‌شده قابل خواندن باشد. PHP سرور به `pdo_pgsql` و برای مرحلهٔ انتقال به `pdo_sqlite` نیاز دارد. مسیر `LEGACY_SQLITE_DATABASE` باید فایل قبلی موجود را نشان دهد. سپس از ریشهٔ Laravel اجرا کنید:

```bash
php artisan config:clear
php artisan migrate --database=pgsql --force
php artisan analytics:transfer-database --source=legacy_sqlite --target=pgsql --dry-run
php artisan analytics:transfer-database --source=legacy_sqlite --target=pgsql
```

`--dry-run` اتصال، ساختار، خالی‌بودن مقصد، تعداد ردیف‌ها و سازگاری مقدارها با کنترل بایت صفر را بررسی می‌کند و داده‌ای نمی‌نویسد. انتقال واقعی شناسه‌ها، JSON و مقدار رمزگذاری‌شدهٔ تنظیمات را حفظ می‌کند؛ جدول‌های مقصد را در تراکنش قفل می‌کند، تعداد ردیف‌ها را می‌سنجد و sequenceها را تنظیم می‌کند. تاریخچهٔ migration مقصد حفظ و فایل مبدأ دست‌نخورده باقی می‌ماند. نقش PostgreSQL باید مجوز درج، قفل و تغییر sequenceهای ساخته‌شده توسط migration را داشته باشد. ساختار دو طرف باید همسان باشد؛ چرخهٔ کلید خارجی، ارجاع به schema دیگر و نام‌های خارج از شناسه‌های ساده با خطا متوقف می‌شوند. این فرمان فایل‌های خارجی SQLite متصل به گزارش‌ها را منتقل نمی‌کند.

گزینه‌های batchهای صف با قالب قابل‌خواندن توسط Repository لاراول در PostgreSQL منتقل می‌شوند؛ برای این تبدیل، دادهٔ سریال‌شده اجرا یا unserialize نمی‌شود. رشته‌های دیگرِ حاوی `NUL` (بایت صفر) با پیام نام جدول/ستون رد می‌شوند و تراکنش مقصد برمی‌گردد؛ انتقال دادهٔ باینری سفارشی به تبدیل اختصاصی نیاز دارد. این کنترل مانع کوتاه‌شدن مقدار در پارامتر متنی می‌شود؛ [قرارداد پارامترهای متنی libpq](https://www.postgresql.org/docs/current/libpq-exec.html#LIBPQ-PQEXECPARAMS) آن‌ها را رشتهٔ پایان‌یافته با صفر تعریف می‌کند.

اتصال‌های گزارش قدیمی SQLite به‌صورت خام حفظ ولی از فهرست منابع پنهان می‌شوند. فرمان انتقال، SQL آن پرسش‌ها را به PostgreSQL تبدیل نمی‌کند؛ برای آن گزارش‌ها یک اتصال مجاز و تعریف پرسش سازگار تنظیم کنید.

برای ثبت جدول‌های PostgreSQL در ماژول، گزینه‌های ابتدای `database/seeders/AnalyticsPostgresSeeder.php` را بررسی کنید: `laravel_connection` نام پروفایل موجود Laravel، `connection_name` عنوان نمایشی و `owner_email` ایمیل کاربر موجود پنل است. اگر فقط یک کاربر وجود دارد، تعیین ایمیل لازم نیست؛ در اجرای داخل پنل، guard واقعی Filament اولویت دارد. `sync=true` ساختار جدول‌ها را از PostgreSQL می‌خواند؛ برای صرفاً ثبت تنظیمات بدون دسترسی به سرور، آن را `false` بگذارید. Seeder جدول، کاربر یا دادهٔ تجاری جدید ایجاد نمی‌کند و اجرای مجدد ویرایش‌های اتصال در پنل را حفظ می‌کند.

```bash
php artisan db:seed --class=AnalyticsPostgresSeeder
php artisan view:clear
php artisan filament:clear-cached-components
```

برای انتقال این تغییر به پروژهٔ داخل شبکه، فایل‌های PHP تغییرکرده در `app/Domain/Analytics`، `app/Models/AnalyticsConnection.php`، `app/Http/Controllers/AnalyticsController.php`، Resource اتصال و Page مرور دیتابیس، فرمان `app/Console/Commands/TransferAnalyticsDatabase.php` و دو Seeder `AnalyticsPostgresSeeder` و `AnalyticsDemoSeeder` را منتقل کنید. تغییرات `config/analytics.php`، پیش‌فرض و پروفایل `legacy_sqlite` در `config/database.php` و پیش‌فرض PostgreSQL در `config/queue.php` را با کانفیگ موجود ادغام کنید؛ اتصال‌های دیگر و `APP_KEY` پروژهٔ مقصد را حفظ کنید. حذف ساخت فایل SQLite از scriptِ `post-create-project-cmd` در `composer.json` نیز اعمال شده و به نصب پکیج تازه نیاز ندارد. برای رابط، نسخهٔ جدید `resources/js/analytics.js`، `analytics/connections.js` و `analytics/notebook.js` و **کل `public/build` شامل manifest** را منتقل کنید؛ build آماده است و npm داخل شبکه لازم نیست.

## داشبورد از داده‌های موجود ClickHouse

`AnalyticsClickHouseSeeder` مستقل از `AnalyticsDemoSeeder` است و از جدول یا View موجود در ClickHouse گزارش و داشبورد می‌سازد. داده و جدول در ClickHouse ایجاد یا تغییر نمی‌دهد و `DB_CONNECTION` اصلی Laravel را عوض نمی‌کند. جدول‌های انتخاب منبع گزارش، تمام جدول‌ها و Viewهای **دیتابیس تنظیم‌شده در اتصال** هستند؛ به مدل‌های Eloquent، `$fillable` یا جدول انتخاب‌شده برای داشبورد محدود نمی‌شوند. برای دیتابیس دیگر، اتصال جدا بسازید. نمایش نام‌ها همچنان به‌صورت پیش‌فرض نام واقعی دیتابیس است.

اطلاعات اتصال از همان پروفایل `clickhouse` در `config/database.php` خوانده می‌شود؛ تنظیمات نصب‌شدهٔ پکیج Laravel، شامل `host`، `port`، `database`، `username`، `password` و `https`، قابل استفاده‌اند. فایل کانفیگ جدا یا متغیر محیطی مخصوص ماژول لازم نیست. فقط انتخاب‌های داشبورد را در آرایهٔ `$options` ابتدای خود `AnalyticsClickHouseSeeder` تنظیم کنید:

```php
public array $options = [
    'owner_connection' => 'pgsql',
    'owner_email' => 'admin@example.com',
    'connection_id' => null,
    'laravel_connection' => 'clickhouse',
    'source' => 'incidents',
    'date_field' => 'event_time',
    'category_field' => null,
    'value_field' => null,
    'dashboard_name' => 'نمای کلی ClickHouse',
];
```

مالک، **کاربر ورود به پنل Filament در مدل `User` و PostgreSQL** است؛ حساب محصول Metabase جداگانه برای مالکیت این ماژول استفاده نمی‌شود. در زمینهٔ یک پنل، ابتدا `Filament::auth()->user()` با guard همان پنل خوانده می‌شود؛ خارج از زمینهٔ پنل، `Auth::user()` لاراول استفاده می‌شود. اگر کاربر احرازهویت شده باشد، اتصال و شناسهٔ خودش مبناست و نیازی به انتخاب دستی ایمیل نیست. اگر `owner_email` تنظیم شده باشد، باید با همان کاربر مطابقت داشته باشد. پنل با guard جداگانه از کاربر واردشده به guard دیگری استفاده نمی‌کند. درخواست وبِ مهمان اجازهٔ انتخاب مالک از دیتابیس را ندارد.

در اجرای معمول `php artisan db:seed` نشست ورود مرورگر وجود ندارد و Auth کاربری برنمی‌گرداند؛ فقط در این مسیر بدون کاربر جاری، fallbackِ Eloquent اجرا می‌شود. `owner_connection` نام اتصال کاربران در `config/database.php` است و به‌صورت پیش‌فرض `pgsql` انتخاب می‌شود؛ اگر نام اتصال PostgreSQL پروژه متفاوت است، همان نام را قرار دهید. ایمیل نمونه را با ایمیل ورود به Filament جایگزین کنید؛ اگر در دیتابیس کاربران پنل فقط یک کاربر وجود داشته باشد، `owner_email=null` هم قابل استفاده است. Seeder مدل `User` یا اتصال پیش‌فرض برنامه را تغییر نمی‌دهد و پیش از درخواست ClickHouse بررسی می‌کند که اتصال مالک، همان فضای کاربران مدل `User` و دیتابیس جدول‌های `analytics_*` باشد؛ شناسهٔ همسان در یک دیتابیس نامرتبط معتبر نیست. اتصال‌های alias همان دیتابیس قابل استفاده‌اند؛ برای PostgreSQL، تنظیمات دیتابیس/میزبان/پورت/schema/نقش باید سازگار باشند.

پیش‌فرض جدول `incidents` و ستون `event_time` مطابق تصویر مدل `Alert` است. نام واقعی منبع را می‌توان ساده (`incidents`) یا کامل (`warehouse.incidents`) نوشت. گزینه‌های `category_field` و `value_field` اختیاری‌اند؛ با نام ستون دسته‌بندی و عددی واقعی پر شوند. اگر منبع تاریخ ندارد، `date_field=null` بگذارید. هیچ رمز اتصالی در Seeder قرار نمی‌گیرد.

اگر `connection_id` تعیین نشده باشد، Seeder تنها اتصال ClickHouse همان مالک را استفاده می‌کند. در نبود آن، تنظیمات `database.connections.clickhouse` موجود در پروژه را وارد ماژول تحلیل می‌کند؛ نام پروفایل با گزینهٔ `laravel_connection` قابل تغییر است. این مسیر، کانفیگ را می‌خواند و به PDO ClickHouse متکی نیست؛ فیلد `user` نیز به `username` و `https` به تنظیم HTTPS ماژول نگاشت می‌شود. پورت از `http_port` و سپس `port` همان پروفایل گرفته می‌شود و باید **HTTP/HTTPS** باشد؛ پورت‌های Native رایج `9000` و `9440` پذیرفته نمی‌شوند. اگر چند کاربر یا چند اتصال ClickHouse وجود داشته باشد، مالک/شناسه باید صریح تعیین شوند تا اتصال دیگری انتخاب نشود. اگر اتصال از قبل در ماژول ثبت شده باشد، تنظیمات ذخیره‌شدهٔ همان اتصال استفاده می‌شود؛ برای تغییر میزبان/رمزِ آن از فرم ویرایش اتصال استفاده کنید.

پس از تنظیم، از پوشهٔ `app` اجرا کنید:

```powershell
php artisan config:clear
php artisan db:seed --class=AnalyticsClickHouseSeeder
```

داشبورد همیشه تعداد رکوردها و جدول جزئیات دارد؛ با ستون تاریخ، روند روزانه و فیلتر تاریخِ متصل به همهٔ کارت‌ها اضافه می‌شود؛ با ستون دسته‌بندی، Donut و با ستون عددی، مجموع آن ستون ساخته می‌شود. ساختار، نوع و قابل‌نمایش‌بودن ستون‌ها پیش از ذخیرهٔ گزارش‌ها بررسی می‌شود. اجرای دوباره فهرست همهٔ جدول‌ها را همگام می‌کند، ولی گزارش‌ها، نام و چیدمان داشبورد ساخته‌شده را تکرار یا بازنویسی نمی‌کند. برای ساخت داشبورد منبع دیگر، گزینهٔ `source` را تغییر دهید.

کاتالوگ ClickHouse از محدودیت تعداد ردیف پیش‌نمایش جداست؛ همگام‌سازی باید کامل انجام شود یا خطا بدهد. Viewها برچسب «نمای داده» دارند و موتور اصلی نیز در کاتالوگ نگه داشته می‌شود. نام دیتابیس/جدول دارای نقطه و کاراکترهای escape در Query و Join حفظ می‌شوند. پاسخ HTTP موفقی که JSON آن حاوی خطای اجرای Query باشد پذیرفته نمی‌شود و کاتالوگ قبلی حفظ می‌شود. قواعد شناسه‌ها و محدودیت نتیجه با [مستندات رسمی Syntax](https://clickhouse.com/docs/reference/syntax) و [Query complexity](https://clickhouse.com/docs/concepts/features/configuration/settings/query-complexity) بررسی شده‌اند. ارتباط HTTP ماژول فقط خواندنی است. آزمایش محلی این مسیر با پاسخ HTTP شبیه‌سازی‌شده انجام می‌شود؛ بررسی زنده به سرور ClickHouse قابل دسترس نیاز دارد.

برای انتقال آفلاین قابلیت Seeder، `AnalyticsClickHouseSeeder.php` و نسخهٔ جدید `ClickHouseDriver.php` و `ReportRunner.php` را منتقل کنید؛ پروفایل ClickHouse موجود در `config/database.php` مقصد را حفظ کنید. فایل کانفیگ اختصاصی قبلی حذف شده است و خود این مسیر به پکیج جدید نیاز ندارد؛ برای رابط بومی جدید، فایل‌ها و build بخش انتقال آفلاین بالا را نیز منتقل کنید. سپس همگام‌سازی اتصال، همهٔ جدول‌ها و Viewها را در انتخاب منبع گزارش در دسترس قرار می‌دهد. برای این مسیر، فرمان `db:seed` باید کلاس `AnalyticsClickHouseSeeder` را اجرا کند؛ `AnalyticsDemoSeeder` اکنون نام سازگار با نسخهٔ قبل برای Seeder اتصال PostgreSQL است.

## ساختار کد و اعتبارسنجی

- `app/Filament/Resources/AnalyticsDashboardResource`، `AnalyticsReportResource` و `AnalyticsConnectionResource`: جدول‌ها، جست‌وجو، فیلتر، فرم و Actionهای بومی پنل و محدودسازی رکوردها به کاربر مجاز.

تست‌های بک‌اند علاوه بر جریان‌های قبلی، چهار نوع Join واقعی، چند شرط ON، فرمول و تزریق، SQL اختیاری، مراحل متوالی، Join و فرمول پس از خلاصه‌سازی، فیلتر و پیشنهاد مقادیر و گروه‌بندی زمانی در مراحل بعد، متادیتا، تغییر منبع و cache و دسته‌بندی NULL را پوشش می‌دهند. سناریوهای مرورگر شامل ساخت و ذخیرهٔ پرسش چندمرحله‌ای، Join و فرمول، SQL/متغیر و تنظیم نمودار، Pivot/قیف، متادیتا و همگام‌سازی، انتخاب فیلتر روی کارت و drag/resize هستند. اتصال SQLite واقعی است؛ آزمون ClickHouse از HTTP شبیه‌سازی‌شده استفاده می‌کند و PostgreSQL از نظر تولید SQL بررسی شده است. بازنویسی پارامتر ClickHouse متن‌های نقل‌قول‌شده، نام ستون و comment را نادیده می‌گیرد و فقط placeholder واقعی را تبدیل می‌کند.

در بازبینی ۲۰۲۶-۱۰-۱۷، اجرای کامل بک‌اند پیش از ساده‌سازی تنظیمات با **۱۴۷ تست و ۱۴۲۱ assertion** موفق بود. آخرین اجرای هدفمند Seeder پس از اضافه‌شدن Auth با **۳۷ تست و ۴۸۱ assertion** موفق بود؛ شامل اولویت guard واقعی Filament، Laravel Auth خارج از پنل، رد درخواست وب مهمان و ایمیل مالک ناسازگار، کاربر حذف‌شده/ذخیره‌نشده، انتخاب اتصال نام‌گذاری‌شدهٔ `pgsql` روی دیتابیس ایزوله، رد حساب Metabase جداگانه و برخورد شناسه در دیتابیس نامرتبط، پروفایل پکیج با `https=false/true`، استفاده از پیش‌فرض‌های Seeder و مستقل‌بودن از کانفیگ قدیمی. این تست‌ها از SQLite حافظه‌ای و HTTP شبیه‌سازی‌شده استفاده می‌کنند و آزمون زندهٔ PostgreSQL/ClickHouse نیستند. **۱۹ تست Node**، شامل پنج تست نام‌های چندزبانه، نه تست نمایش Drill و پنج تست تولید شناسهٔ سازگار با HTTP، نیز در بازبینی رابط همین روز موفق بودند.

در آخرین بررسی PostgreSQL در ۲۰۲۶-۱۰-۱۸، مجموعهٔ Resourceهای بومی PHP با **۱۴ تست و ۱۷۳ assertion** موفق بود؛ سه تست جدید، ثبت/ویرایش بدون سرور و نمایش صحیح خطای میزبان را بررسی می‌کنند. تست خطای میزبان پیش از اصلاح مسیر خطا شکست خورد و پس از اصلاح موفق شد. Pageهای ویرایشگر **۷ تست / ۵۴ assertion** و **۱۹ تست Node** در اجرای قبلی موفق بودند و در این مرحله دوباره اجرا نشده‌اند. کپی مستقل گزارش و فیلتر Donut/Pivot همچنان در مجموعهٔ Resourceها پوشش دارند.

در بررسی PostgreSQL، پوشش مرورگر **۴۲ سناریوی مستقل Chrome** داشت: ۳۶ سناریوی منتقل‌شده، چهار سناریوی یکپارچگی بومی Filament و دو سناریوی PostgreSQL. در بازبینی بازطراحی قبلی، اجرای اصلیِ ۳۹ سناریو، **۳۵ موفق** و چهار شکست مربوط به helperهای تست داشت؛ پس از اصلاح helperها، اجرای هدفمند **۱۰ سناریو، همگی موفق بود** (حدود ۱۱٫۴ دقیقه). این اجرا چهار مورد قبلی و سناریوی پاسخ دیررس پنجره را شامل می‌شود؛ سناریوی دیررس روی build قبلی `TypeError` را بازتولید و روی build اصلاح‌شده موفق شد. هر ۴۰ سناریوی قبلی در مجموع این اجراها تأیید شدند؛ اجرای یک‌جای مجموعهٔ نهایی انجام نشده است. دو سناریوی جدید PostgreSQL نیز **هر دو موفق شدند** (حدود ۴٫۵ دقیقه): ثبت و ویرایش واقعی فرم، حفظ رمز، خطای میزبان، جلوگیری از ذخیره پس از آزمون ناموفق و ذخیره با خاموش‌کردن آزمون اتصال. این بررسی‌ها بدون نصب PostgreSQL، همراه با اتصال واقعی ناموفق به یک پورت بستهٔ محلی انجام شدند.

در بازبینی بارگذاری داخل شبکه در ۲۰۲۶-۱۰-۱۸، **۳۳ تست PHP / ۲۸۰ assertion** شامل assetها، سایدبار، Resourceها و Pageهای بومی موفق شدند. سه تست سایدبار پس از اصلاح نهایی قالب نیز دوباره موفق شدند. پوشش مرورگر با سه سناریوی حافظهٔ سایدبار و یک سناریوی جداسازی فونت به **۴۶ سناریو** رسید. در این مرحله **شش سناریوی هدفمند، همگی در اجراهای نهایی خود موفق شدند**: پنج مورد روی میزبان HTTP شبیه شبکه با hot قدیمی و SPA واقعی (سایدبار، UUID روی HTTP، فونت و هندسهٔ نمودار در دو تم و موبایل) و یک مورد جداسازی فونت روی آدرس محلی قابل دسترس. نخستین اجرای مورد آخر به محدودیت DNS نگاشت‌شدهٔ Chrome در `route.fetch` برخورد کرد؛ پس از اجرای محلی، رقابت پاک‌سازی interception خود تست نیز اصلاح و تست دوباره موفق شد. در بازتولید جداگانه، قالب اصلی Filament با مقدار قدیمی گروه ثابت خطای دقیق `null.classList` داد؛ قالب اصلاح‌شده با همان ورودی، بدون خطای JavaScript و بدون درخواست پورت `5173` پیمایش Livewire را حفظ کرد. نمودار و سه ردیف نتیجهٔ واقعی هنگام معلق‌بودن فونت نامرتبط نمایش داده شدند؛ گزارش و داشبورد آزمایشی پاک شدند. این‌ها آزمون محیط محلی‌اند و دسترسی مستقیم یا اندازه‌گیری سرعت سرور داخل شبکهٔ کاربر انجام نشده است؛ کل مجموعهٔ ۴۶ مورد در این مرحله یک‌جا اجرا نشد.

پس از حذف دکمهٔ تکراری «بازگشت»، دو سناریوی «فرم‌های بومی دیتابیس/گزارش و کپی گزارش» و «بررسی کنترل‌های تکراری رابط» روی build آخر **هر دو موفق شدند** (حدود ۵٫۵ دقیقه). این اجرا، مسیر و بازخوانی گزارش، کپی مستقل، فرم‌های سه درایور و وجود یک کنترل بازگشت در Notebook و SQL را همراه با ظاهر روشن/تیره تأیید می‌کند.

تست‌های Chrome رنگ واقعی Donut در منو و نتیجه، رنگ اختصاصی ویجت، NULL/متن تهی، تغییر نوع نمایش و حفظ رنگ سفارشی، Sort/Limit/Join/فرمول، ذخیره/بازکردن، Tooltip، کنترل اصلی Filament و حالت سیستم، حفظ منو/پنجره/تغییرات موقت، رنگ سری پس از فیلتر، هر دو شکل گیج و موبایل را پوشش می‌دهند. برچسب‌های محور افقی با اندازه‌گیری فونت واقعی در دسکتاپ و عرض ۳۹۰ پیکسل بدون چرخش و هم‌پوشانی بررسی می‌شوند. سناریوهای بومی، حفظ منوهای موجود پنل، انتخاب منوی فعال، فرم‌های سه درایور، مسیر مستقیم رکورد، refresh، عقب/جلو و مودال/slide-over واقعی را بررسی می‌کنند. سناریوهای نام‌گذاری، فرم دو زبان، نام خام پیش‌فرض، حفظ نام‌ها پس از Sync، Join و فرمول با کلید اصلی، تم پنل و کوچک‌شدن کنترل زبان هنگام resize بدون ازدست‌رفتن حالت صفحه را بررسی می‌کنند؛ لغو افزودن پرسش و استقلال فیلتر ناوبری نیز پوشش داده شده است. نتیجهٔ داده‌ها با SQL مستقل مقایسه می‌شود.

در بازبینی تغییر پیش‌فرض PostgreSQL در ۲۰۲۶-۱۰-۱۹، اجرای کامل بک‌اند پیش از اصلاح تکمیلی انتقال batchها با **۲۲۲ تست و ۲۱۷۰ assertion** و هر **۱۹ تست Node** موفق بود. پس از اصلاح batchها و کنترل NUL، مجموعهٔ انتقال با **۱۴ تست و ۱۵۷ assertion** دوباره موفق شد؛ خواندن batch و cache با Repository واقعی Laravel، حفظ فایل مبدأ، رد مقدار ناسازگار در dry-run و rollback انتقال واقعی را پوشش می‌دهد. بررسی Pint نیز موفق است. هر دو سناریوی Chrome در اجرای نهایی موفق شدند: پیش‌فرض PostgreSQL، دقیقاً دو درایور، نبود مسیر SQLite، تغییر پیش‌فرض‌ها هنگام تعویض موتور، ثبت/ویرایش واقعی، حفظ رمز و کنترل خطای اتصال. helper جست‌وجوی تست اکنون تکمیل درخواست debounce فیلامنت را پیش از کلیک ردیف انتظار می‌کشد. fixtureهای Query در تست‌های PHP همچنان SQLite ایزوله هستند؛ تست‌های سیاست منابع، فهرست مجاز واقعی دو درایور را بررسی می‌کنند. اتصال زنده و انتقال روی PostgreSQL به محیط شبکه موکول شده است.

Vite build و بررسی JavaScript موفق‌اند. تصاویر ویجت‌های روشن/تیره/موبایل، منوی Donut و فرم‌های اتصال، Notebook، SQL، فیلتر، ویرایش داشبورد و رفتار کلیک در `tests/Browser/artifacts` تولید و بازبینی شدند.

```powershell
& '..\.tools\php\php.exe' artisan test --compact
& '..\.tools\node\node.exe' tests/Unit/DrillPresentation.test.mjs
& '..\.tools\node\node.exe' tests/Unit/MetadataNames.test.mjs
& '..\.tools\node\node.exe' tests/Unit/Uid.test.mjs
$env:PATH = "$PWD\..\.tools\node;" + $env:PATH
npm.cmd run test:browser -- tests/Browser/postgres-connections.spec.js tests/Browser/postgres-table-names.spec.js
```

فرمان مرورگر بالا، دو سناریوی فرم PostgreSQL/ClickHouse و یک سناریوی نمایش نام جدول‌ها را بدون نیاز به سرور PostgreSQL اجرا می‌کند. سناریوی نام‌ها با fixture پاسخ API، انتخاب جدول در سه زبان و SQL فیزیکی تولیدشده را در پنل واقعی بررسی می‌کند؛ تست PHP جداگانه، قالب‌بندی کاتالوگ واقعی ذخیره‌شده را بررسی می‌کند. سناریوهای قدیمی‌ترِ گزارش و نمودار به fixture فروش SQLite وابسته‌اند؛ برای اجرای آن‌ها روی نسخهٔ فعلی باید منبع و دادهٔ آزمایشی PostgreSQL و انتظارهای SQL آماده شود. آمار اجرای آن سناریوها در بندهای قبلی، سوابق نسخه‌های قبل است و اجرای کامل آن مجموعه روی PostgreSQL در این تغییر انجام نشده است.

تست مرورگر از Chrome نصب‌شده استفاده می‌کند؛ با `CHROME_PATH` مسیر مرورگر و با `ANALYTICS_URL` آدرس برنامه را تغییر دهید. برای حساب دیگری، `ANALYTICS_EMAIL` و `ANALYTICS_PASSWORD` را تنظیم کنید. حساب فعلی محلی از فایل نادیده‌گرفته‌شدهٔ `.tools/admin.json` خوانده می‌شود. فایل‌های تست ساخته‌شده از API پاک می‌شوند. تصویرهای بررسی رابط در `tests/Browser/artifacts` تولید می‌شوند.

## حدود شباهت به Metabase

برای بازطراحی، سورس محلی `metabase/frontend/src/metabase/querying/notebook` شامل `utils/steps.ts`، `ExpressionStep`، `SortStep`، `LimitStep`، `NotebookStep` و پیش‌نمایش آن، `NotebookCell`، `JoinComplete`، `JoinStrategyPicker` و `SummarizeStep` بررسی شده است. ترتیب بخش‌ها، عملیات روی خروجی خلاصه‌سازی، کارت قابل جابه‌جایی، تغییر جهت Sort، حذف بخش، اعمال Limit در blur، پیش‌نمایش هر بخش و رنگ/دکمه‌های این صفحه از این جریان‌ها پیروی می‌کنند. سقف‌های پیش‌نمایش از `src/metabase/query_processor/middleware/constraints.clj` بررسی شده‌اند. برای سایر صفحات، `admin/databases/components/DatabaseList` و `dashboard/components/DashboardHeader` مبنا بوده‌اند.

برای تعامل داده، سورس `visualizations/components/ClickActions`، تنظیمات رفتار کلیک و اتصال مقادیر، `src/metabase/lib/drill_thru` و انتخاب‌گرهای فیلتر/تاریخ بررسی شده‌اند. نقش ستون و مقدار، تفاوت فیلتر خروجی با رکوردهای زیرین و تفاوت بزرگ‌نمایی زمانی با انتخاب دسته از این جریان‌ها پیروی می‌کنند.

برای رنگ و تعامل Donut، `PieChart/use-chart-events.ts`، `PieChart/definition.ts`، `PieRowsPicker`، `viz-core/shared/settings/pie.ts`، `ui/colors/charts.ts` و `sync-viz-settings.ts` بررسی شده‌اند. حفظ نگاشت رنگ مقدار، اولویت رنگ دلخواه هر دسته، هویت جداگانهٔ NULL و تنظیمات مستقل نتیجهٔ بررسی از این بخش‌ها پیروی می‌کنند. رفتار کارت‌ها در hover/focus/touch نیز با بررسی `DashCard.module.css` و `DashCardVisualization.module.css` تنظیم شده است؛ ظاهر خود ویجت‌ها از تصاویر طرح ارسالی پیروی می‌کند.

مقایسهٔ تصویری پیکسل‌به‌پیکسل با یک Metabase در حال اجرا انجام نشده است. این برنامه همهٔ امکانات محصول Metabase را ندارد: نقشه و بررسی مکانی، automatic insights، توابع expression خارج از فهرست بالا و Window، permission matrix سازمانی/سطح ردیف، embedding عمومی، subscription ایمیلی، sync زمان‌بندی‌شده و cross-database Join خارج از قابلیت فعلی‌اند. مجموعه‌ها یک سطح دارند؛ نتیجه و CSV سقف پیش‌نمایش متناسب با نوع نتیجه را رعایت می‌کنند. تست زندهٔ PostgreSQL و ClickHouse به سرور آن‌ها نیاز دارد که طبق درخواست نصب نشده‌اند.
